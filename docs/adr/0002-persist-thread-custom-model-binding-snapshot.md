# 持久化会话自定义模型绑定快照

会话选择自定义模型时，codeck 按 `threadId` 持久化当次选择的自定义模型配置快照，而不是让会话持续引用目录中的最新配置。快照包含恢复运行时与解释当前模型所需的 `customModelId`、模型标识、上下文窗口、能力声明、来源配置更新时间和会话实际采用的 reasoning 档位，但不包含 provider；provider 在每次运行时重建时从 Codex 当前模型接入配置解析。

没有采用只保存模型字符串或实时引用自定义模型目录的方案。app-server 持久化的会话元数据不足以恢复自定义上下文窗口和 Web 能力声明，而实时引用会使目录编辑或删除在下次恢复时静默改变已有会话，违背“编辑配置不自动切换会话”的语义。

## Consequences

codeck 需要在专用数据目录中使用独立的版本化 JSON 文件保存会话绑定，不能与带有目录修订号的自定义模型目录共用文件，也不能写入 app-server 不支持扩展的 thread metadata。绑定文件采用锁、临时文件和原子替换，损坏时明确报错而不静默重置或降级。

系统还需要处理会话删除后的清理、旧会话无绑定时的兼容以及存储损坏。创建会话、模型切换、reasoning 档位更新和失败恢复必须协调运行时结果与绑定提交，避免二者指向不同模型或 reasoning 档位。目录配置更新后，已有会话继续使用旧快照，直到用户显式重新应用或切换模型。

自定义模型会话在创建或切换核验成功后创建或替换绑定，切换到 app-server 目录模型后移除绑定；会话内 reasoning 档位更新成功时同步绑定。fork 继承来源会话的绑定快照，归档不移除绑定，删除会话时清理绑定。没有绑定的旧会话即使模型标识与自定义模型目录相同，也不能据此自动建立绑定，必须等待用户显式选择。

已有会话的模型切换、重新应用和 reasoning 更新还必须在绑定文件中先原子写入包含旧绑定与目标绑定的操作记录，再修改 app-server 运行时，最后以一次原子写入提交目标绑定并清除操作记录。后端只能在清除操作记录后返回成功；进程中途退出时，下次访问该会话必须先继续应用目标或恢复旧绑定，恢复完成前不能发送 turn。新会话创建和 fork 在 app-server 返回新 `threadId` 后、向前端返回前写入绑定；若在取得 ID 与写入之间退出，产生的无绑定会话仍按 app-server 会话处理，不能根据同名模型自动认领。

操作恢复同时失败时保留操作记录，并允许用户明确选择按旧状态恢复或按原目标快照重试；目标重试不能重新解析目录中的最新配置。恢复命令成功后才能提交相应绑定并清除操作记录，不能提供绕过操作记录继续发送 turn 的路径。

目录变更、绑定变更和操作恢复都必须接入现有审计日志。恢复审计使用原 `operationId`，并记录触发原因、最终绑定版本和恢复结果；日志不得包含任何凭据值、鉴权头或完整 provider 配置。
