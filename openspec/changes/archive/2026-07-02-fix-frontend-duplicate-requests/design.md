## Context

当前前端请求保护分散在组件内部：`ChatInput` 对发送按钮有 in-flight 锁，Skill 列表加载也有 promise 复用；`turn/start` 后端已基于 `clientUserMessageId` 做短期幂等缓存。但会话打开、快照修复、历史分页、新建会话、模型/模式设置、归档/压缩等入口缺少统一纪律。

这类问题在移动端更容易出现：用户可能快速连点、快速返回/进入页面、滚动触顶反复触发分页；开发模式下 React effect 重放也会让网络面板暴露重复请求。仅靠按钮 disabled 或延时防抖不能覆盖 effect、滚动、路由切换和后端副作用。

## Goals / Non-Goals

**Goals:**

- 建立前端请求去重与动作互斥的统一模式，覆盖查询请求和副作用请求。
- 让打开会话、发送消息、新建会话、历史分页和常见会话操作在移动端连点/快速切换下保持单一有效结果。
- 保留并强化关键接口的幂等兜底，避免前端保护失效时产生重复 turn 或重复 thread。
- 用单元测试覆盖重复点击、重复 effect、滚动触顶和失败后重试。

**Non-Goals:**

- 不引入新的远程状态管理库或请求缓存框架。
- 不改变 app-server 协议语义，不重构会话时间线合并逻辑。
- 不把所有请求都做全局缓存；只处理本变更涉及的高风险重复请求。
- 不优化桌面端布局，本项目仍以手机浏览器为目标。

## Decisions

1. 读取类请求使用“keyed in-flight 去重 + 必要时 abort 旧请求”

   - 决策：为会话详情、快照修复、历史分页、模型/设置等读取请求提供稳定 key。同 key 请求正在进行时复用同一个 promise；当页面切换或新一代请求取代旧请求时，使用 `AbortController` 取消旧请求或保证旧结果不会落库。
   - 理由：读取请求重复本身不一定破坏数据，但旧响应覆盖新状态会造成 UI 闪回或 running 状态错误。
   - 替代方案：只保留现有 `cancelled` 标记。该方案能避免 React setState，但请求仍会发出，且 store 层更新仍可能被旧路径触发。

2. 副作用请求使用动作级 pending 锁

   - 决策：为 mutation 建立按动作和资源维度的锁，例如 `startThread:<cwd>`、`archive:<threadId>`、`compact:<threadId>`、`interrupt:<threadId>`、`updateSettings:<threadId>`。重复触发时忽略、复用当前 promise，或禁用触发控件。
   - 理由：副作用请求不能靠 GET 缓存解决，必须把同一用户动作归并成一次执行。
   - 替代方案：使用固定毫秒防抖。该方案会漏掉长请求期间的第二次点击，也会让失败重试窗口变得不清晰。

3. 发送消息继续以 `clientUserMessageId` 作为端到端幂等键

   - 决策：同一次用户发送动作生成稳定 `clientUserMessageId`，前端 in-flight 锁和后端 `turn/start` 幂等缓存都基于这个键工作。失败后允许用户重新发送，但必须生成新的发送动作上下文或明确复用失败消息的重试上下文。
   - 理由：发送消息是最高风险路径，前端锁只能减少重复，后端幂等才能兜住网络重试、双提交和浏览器重放。
   - 替代方案：只按文本/image/Skill payload 去重。该方案会误拦用户连续发送相同内容，也不能区分“同一次提交”和“后续明确重发”。

4. 新建会话使用 client operation id 做前后端双层保护

   - 决策：项目页新建会话先加前端 pending 锁；同时为移动端 `threads/start` 请求增加可选 client operation id，并在短 TTL 内对相同 operation id 返回同一个 thread。该字段向后兼容，旧客户端不传时保持现有行为。
   - 理由：重复新建会话会产生持久资源，单靠前端 disabled 仍无法覆盖网络重试、浏览器重复提交和多入口触发。
   - 替代方案：只在按钮点击后立即跳转。网络慢或接口失败时仍存在多次点击窗口，也无法兜住请求层重放。

5. 设置类 mutation 以后发值为准

   - 决策：模型、推理强度、Plan/Build 模式等设置请求应避免并发乱序。实现上可采用同 key 串行队列、最新值覆盖待发送值，或在响应落地前校验本地期望值。
   - 理由：这些请求可被用户快速切换，旧响应不应覆盖最新选择。
   - 替代方案：每次点击都立即发送且不协调。该方案在网络乱序时会让服务端设置落后于 UI。

## Risks / Trade-offs

- [Risk] 请求去重 key 设计过粗会误拦合法操作。→ Mitigation：mutation key 必须包含资源 id 和动作名；发送消息使用 operation id，不只使用文本内容。
- [Risk] 请求去重 key 设计过细会挡不住重复。→ Mitigation：为每个高风险入口写重复触发测试，验证同一用户动作只产生一次 API 调用。
- [Risk] abort 后错误处理噪声增加。→ Mitigation：将 abort 视为正常取消路径，不展示用户错误。
- [Risk] 设置类请求合并可能让中间状态不落服务端。→ Mitigation：这是预期行为，服务端最终状态应匹配用户最后一次选择。
- [Risk] 后端幂等缓存短 TTL 不能覆盖跨页面长时间重复。→ Mitigation：TTL 只用于短时间重复提交兜底，长期重复应视为新动作。

## Migration Plan

- 先补充失败测试，锁定现有重复请求入口。
- 引入轻量的前端请求协调工具或本地 hook，不引入新依赖。
- 逐步接入会话打开/修复、历史分页、发送消息、新建会话和会话操作。
- 补充后端幂等测试；若扩展 `threads/start`，保持请求参数向后兼容。
- 回滚策略：请求协调层应只包裹调用点，必要时可逐入口移除，不影响 API 基本形状。
