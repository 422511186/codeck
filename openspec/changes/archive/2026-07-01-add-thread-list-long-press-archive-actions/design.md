## Context

项目会话列表位于 `src/app/projects/[projectId]/page.tsx`，当前已通过「进行中 / 已归档」tab 分别拉取 `archived=false` 和 `archived=true` 的会话列表。会话详情页已经支持归档与移出归档，前端 API 层也已有 `codex.archiveThread` 和 `codex.unarchiveThread`。

本项目只面向移动端 Web，列表管理交互应以触摸手势为主。项目页已经存在长按项目条目弹出底部菜单的产品模式，因此会话列表可以沿用同类手势和菜单心智。

## Goals / Non-Goals

**Goals:**

- 用户在项目会话列表长按会话条目后，可以不进入详情页就执行归档或移出归档。
- 菜单动作根据当前 tab 显示：进行中显示「归档」，已归档显示「移出归档」。
- 操作成功后列表立即反映归档状态变化，条目从当前 tab 移除。
- 长按触发菜单后不触发行点击跳转，避免移动端误操作。
- 操作失败时保留原列表，并向用户展示错误信息。

**Non-Goals:**

- 不新增后端 API、协议字段或数据模型。
- 不实现批量选择、滑动操作、桌面端右键菜单或键盘快捷键。
- 不改变会话详情页已有归档与移出归档行为。
- 不在列表内读取完整 thread detail；列表操作只依赖已有 `ThreadSummary` 和 threadId。

## Decisions

1. 使用长按打开底部操作菜单，而不是在条目上常驻按钮。

   移动端列表空间有限，常驻按钮会降低信息密度并增加误触区域。长按与项目列表现有交互一致，也符合用户提出的入口要求。备选方案是左滑操作，但项目中没有现成滑动菜单模式，容易引入额外手势冲突。

2. 归档与移出归档复用现有 `codex.archiveThread` / `codex.unarchiveThread`。

   后端已有 `POST /api/codex/threads/{threadId}/archive` 和 `/unarchive`，本变更只改变列表页入口，不需要协议扩展。`unarchiveThread` 虽返回 `ThreadDetail`，列表页无需依赖该详情来更新当前 tab，只需确认请求成功并移除当前条目。

3. 操作成功后从当前列表本地移除条目。

   当前 tab 的查询条件在操作后已经不再包含该条目：进行中归档后应进入已归档 tab，已归档移出后应进入进行中 tab。本地移除能提供即时反馈，并避免等待重新拉取造成重复点击。后续切换 tab 或重新进入页面时会从后端重新拉取权威列表。

4. 长按状态与点击跳转分离。

   条目需要在 `pointerdown` 后启动 500ms 定时器，在 `pointerup`、`pointercancel`、明显移动或离开时取消。长按成功打开菜单后，应阻止该次点击继续触发 `router.push`。这可以通过记录刚触发长按的 threadId 或使用事件抑制标记完成。

5. 失败时不做乐观移除。

   归档状态属于服务端状态，若请求失败后再回滚列表，会增加边界复杂度。保持请求成功后再移除条目更稳妥；失败时只展示错误并关闭或保留菜单，由实现阶段按现有页面错误模式选择。

## Risks / Trade-offs

- [Risk] 长按和滚动手势冲突，用户滚动列表时可能误触发菜单。→ 在移动距离超过阈值、`pointercancel` 或滚动开始时取消长按定时器。
- [Risk] 长按触发后浏览器仍派发 click，导致用户被带入会话详情。→ 在长按成功后记录抑制标记，下一次同条目的 click 必须被忽略。
- [Risk] 请求期间重复点击菜单项造成重复请求。→ 菜单动作需要进入 pending 状态，禁用当前操作按钮或忽略重复提交。
- [Risk] 已归档恢复后条目从当前 tab 消失，用户可能不知道去了哪里。→ 操作完成后维持当前 tab，并可通过短错误/状态提示说明结果；切换到对应 tab 可看到移动后的会话。
